# 从零理解路由与作用域

这份文档先讲设计动机，再讲代码。不要从 DirectStorageRoutingIT 的 Fixture 开始：它同时装配数据库、事务、幂等状态机和观测断言，是验证入口，不是入门入口。

## 1. 要解决的三个问题

1. 一个用户的数据应该进入哪个分片？分片算法负责。
2. 这个分片对应哪个库、哪张表？物理映射负责。
3. 同一次同步执行中，订单和幂等操作如何使用同一分片？执行作用域负责传递结果。

真正执行 SQL 是 relational-access / JDBC Repository 的工作；提交和回滚是 transaction / Spring 集成的工作。路由组件不实现分布式事务，不迁移历史数据，也不自动重写任意 SQL。

## 2. 一个例子

业务按 user_id 路由，幂等按 request_id 区分重复请求。这两个 key 可以不同。

假设 user_id 算出 shardId=37，10 库每库 10 表：databaseIndex=37/10=3，localTableIndex=37%10=7。

| 内容 | 库 | 表（库内编号） |
| --- | --- | --- |
| 订单 | db_03 | business_order_07 |
| 幂等 | db_03 | iron_idempotency_record_07 |

幂等共享订单的分片结果，使用自己的表映射。不能拿订单物理表名执行幂等 SQL，也不能再次 hash request_id 把幂等数据送到别的库。全局编号方案则可将两张表的后缀都映射为 37。

数据写入、查询、重试必须使用一致的路由依据。改变分片总数会改变哈希结果，这不等于完成数据扩容迁移。

## 3. 包和阅读顺序

| 包 | 类型 | 读的时候回答什么问题 |
| --- | --- | --- |
| api.key | ShardValue、ShardKey、CompositeShardKey | 按什么字段分？ |
| api.route | RouteContext | 一次计算需要什么输入？ |
| api.route | ShardRouteInfo | 逻辑分片编号是什么？ |
| api.route | PhysicalStorageLocation | 实际在哪个库、哪张表？ |
| api.route | StorageRoute、StorageRouteMode | 如何保存完整结果及访问形态？ |
| api.resolver | ShardResolver、StorageRouteResolver | 谁负责计算？ |
| api.mapping | RouteMappingStrategy、TableIndexMode | 如何将编号变为物理名称？ |
| api.context | StorageRouteContext、StorageRouteScope | 如何传递结果和管理生命周期？ |
| api.exception | StorageRoutingException | 如何报告非法模型或作用域操作？ |

core.resolver 实现计算，core.mapping 实现物理命名，core.context 实现执行期绑定。无需为每个类单独建一个包；同一职责的类放在一起。

本次分包是源码 import 变更，不保留旧包的 Deprecated 别名。仓库内引用已迁移，仓库外调用者需更新 import 并重新编译。数据库结构、键编码、哈希算法及表编号规则不变。

## 4. 先理解纯计算，不引入 ThreadLocal

业务组装 CompositeShardKey，放入 RouteContext。DefaultStorageRouteResolver 先调用 ShardResolver，再调用 RouteMappingStrategy，最后组装 StorageRoute。

HashShardResolver 在总分片数 N 下执行 Math.floorMod(hashInput.hashCode(), N)，得到 0 到 N-1。除以每库表数得到库编号，取余得到库内表编号。单键使用规范值文本，多键使用 canonicalForm；canonicalForm 避免字段拼接歧义，不保证哈希无碰撞。

多个键不意味着可以分别按其中任意一个键查询：tenant+order 的组合路由需要稳定提供这个组合。

DefaultStorageRouteResolver 使用构造时注入的 mapping，RouteContext.logicalTable 只是输入信息，不会自动寻找对应映射器。

入门示例：storage-routing-core/src/test/java/com/xjtu/iron/storage/routing/core/learning/RoutingBasicsTest.java。只有一个方法，按注释从输入读到作用域，无数据库、无 Spring、无复杂 Fixture。

## 5. 为什么需要 ThreadLocal

所有方法都显式传 StorageRoute 也能实现路由。但是会让原本通用的幂等核心 API、Repository 调用链携带基础设施参数。

当前选择是在同步调用入口绑定一次；深层集成代码读取同一上下文实例中的当前路由。ThreadLocal 让线程 A 的绑定不影响线程 B。

代价是隐式依赖、严格生命周期，以及不自动跨线程传播。它不是全局缓存，不是分片算法，不是事务管理器。异步线程、MQ 消费者必须在自己的执行入口建立路由与事务，不能把 scope 句柄跨线程关闭。

## 6. 为什么保留嵌套恢复

ThreadLocal 解决线程隔离；嵌套恢复解决同一线程中不同作用域的生命周期。二者不是一回事。

外层绑定 A，内层临时绑定 B：进入内层读到 B；内层结束恢复 A；外层结束清空。如果只用 set/remove，内层 remove 会破坏外层仍然需要的 A。

这只是上下文恢复，不代表允许在同一个本地事务里跨库。数据源事务兼容性由事务集成层检查。正常的“业务预绑定 + 幂等执行”不会再开一层：幂等装饰器发现已有路由就直接复用。

实现现在保存当前 scope，每个 scope 记住 previous。无需单独维护 Deque；每次 open 都创建不同句柄，按句柄身份检查后进先出，避免同一个 route 绑定两次时误判关闭顺序。current() 在未绑定时不创建空集合。错误线程关闭会被拒绝；错误关闭顺序会清理当前上下文并抛错；成功关闭后重复 close 无副作用。

## 7. 最后才接上幂等与事务

首选用法：业务按稳定业务键解析并打开 scope，然后调用 IdempotencyExecutor；所有要原子提交的业务 SQL 放在 callback 中。StorageRouteAwareIdempotencyExecutor 看到已有 route 直接委托核心执行器。

| 阶段 | 传播 | 动作 |
| --- | --- | --- |
| Tx-A | REQUIRES_NEW | 抢占幂等状态，提交 PROCESSING |
| Tx-B | REQUIRED | 业务 SQL 与 markSuccess 使用同一事务连接 |
| Tx-C | REQUIRES_NEW | 普通业务失败后，在 B 回滚后独立记录失败 |

A/B/C 共享数据源选择，不是一个大事务，也不要求三个阶段一直持有同一物理连接。业务失败后保留 FAILED 幂等记录是正常行为。提交结果未知和所有权失效有独立处理语义。

业务示例走 RelationalTemplate + SpringTransactionAwareConnectionProvider；幂等 Repository 走 JdbcExecutionManager。这两条路径使用同一 DataSource 实例与事务资源，才能复用 B 的连接。相同 JDBC URL 不能代替相同资源绑定。

如果外层已有同数据源事务，B 会加入外层事务；execute 返回不等于外层已提交。外层后来回滚会撤销业务和 SUCCESS，A 的 PROCESSING 仍保留，需要后续恢复。

备用用法：业务没绑定时，默认工厂将幂等 key 组装成分片键，装饰器解析一次并打开 scope。业务 callback 仍须使用当前 shard 对自己的表做映射；组件不会拦截任意业务 SQL 自动改库。此用法要求后续业务读写能稳定恢复同一落点。

## 8. 按四次阅读逐步学习

1. 只看 key、RouteContext、HashShardResolver，不看任何 Spring 类。
2. 看 mapping 与 StorageRoute，运行 RoutingBasicsTest，观察业务表和幂等表复用 shard。
3. 单独看 ThreadLocalStorageRouteContext 与作用域测试，理解 open、previous、close。
4. 再看幂等装饰器和事务协调器；最后用 DirectStorageRoutingIT 验证连接与事务边界。

不要一次追进所有构造器。先回答“这一步输入是什么、输出是什么、谁负责下一步”，再研究装配。
